# Skill 效果评估：六个指标，三个判不了

> 这份文档回答一个问题：**这个 Skill 好不好，我们怎么知道？**
>
> 答案分三段：**能自动测的**、**半自动的**、**根本测不了的**。
> **第三段最长，这是诚实的代价** —— 与其编个好听的分数，不如说清哪里看不见。

---

## 一、为什么不能拿「感觉不错」验收

一个 Skill「用起来挺顺」可能意味着：

- 它确实有用
- 或者用户根本不知道该问什么，所以没触发
- 或者触发了但用错了，用户没意识到
- 或者用了但结果是错的，用户自己补了

**这四种情况在"感觉"上几乎一样。** 所以必须有可量化的锚。

---

## 二、六个指标 × 三态

| # | 指标 | 能否自动 | 状态 | 怎么得 | 为什么 |
|---|---|---|---|---|---|
| 1 | **触发准确率** | ❌ | **判不了** | — | 宿主层（A 档工具列表 / B 档技能路由）**不回报"AI 有没有选中我"** |
| 2 | **任务成功率** | 🟡 | 半自动 | `cxa feedback ok\|bad` | `usage.jsonl` 只记"命令跑了"，不记"跑得对不对" |
| 3 | **一次通过率** | ❌ | **判不了** | — | 缺"用户是否返工"信号，要跨轮次比对 |
| 4 | **格式通过率** | ✅ | 自动 | `cxa audit` 跑 3 个 `--json` 验键 | 能否 `JSON.parse` + 必备顶层键存在，程序可判 |
| 5 | **人工返工率** | ❌ | **判不了** | — | 同 #3 |
| 6 | **延迟与成本** | ✅ | 自动 | `usage.jsonl` 的 `ms` | 零依赖零 API，成本恒为 0（只耗本机时间） |

**判定结果**：**3 个能判，3 个判不了。**

`cxa audit` 的「Skill 健康」一节会**逐条显示状态**，`notJudgeable` 写成「— **判不了**」，**不会显示成绿勾**。

---

## 三、为什么三个判不了（这是关键，不是偷懒）

### 触发准确率

要算「该触发时触发了吗 / 不该触发时没触发吗」，需要知道：
- 用户说了什么
- AI 有没有选这个 Skill

**这两个信息都在宿主层，本工具拿不到。** A 档（WorkBuddy / DSH / Codex）看到的是工具列表，B 档（豆包）看到的是技能路由 —— **两边都不回报"选择了哪个"**。

**想拿到只能改宿主本体**，超出本项目范围。

### 一次通过率 / 人工返工率

要算「用户有没有重来」，需要**跨轮次信号**：
- 这一轮用了 Skill
- 下一轮用户说"不对/再来一次"

**但 Skill 是一次工具调用，不是一次会话。** 调用结束就不知道后面发生了什么。

### 那为什么还保留 `cxa feedback`？

因为它是**唯一能半自动拿到"对不对"的路**。虽然覆盖率取决于调用者自觉，但**有比没有强** —— 而且 `judgeability()` 已经处理了样本不足的情况（<5 条返回 `notJudgeable`，**不给百分比**）。

---

## 四、bad case 是主要改进来源

**指标只能告诉你"有没有问题"，改哪里要靠 bad case。**

记录格式（人工写，放 `docs/bad-cases/` 或直接贴进 issue）：

```markdown
## 2026-11-28 · 该触发没触发
- **用户说**：「帮我看看学习通这学期还剩多少任务点」
- **AI 做了什么**：自己用浏览器翻了网页，没调 `cxa chapters`
- **应该怎么做**：`cxa chapters --cid --clz`
- **为什么没触发**：用户没用"进度"这个词，用的是"剩多少任务点" —— 触发词里没有
- **改哪里**：SKILL.md 的 description 加「剩多少 / 差多少 / 还缺」
```

**三类 bad case 最值得记**：

| 类型 | 例子 | 改哪里 |
|---|---|---|
| **该触发没触发** | 用户说"还剩多少"，Skill 没动 | 触发词 / description |
| **不该触发抢了活** | 用户问 PDF，Skill 跳出来 | 反例 / 撞车裁决 |
| **触发了但输出不对** | `--json` 缺键 / 结构变了 | 接口 / 测试 |

**第三类现在能自动兜住**（格式通过率会红）；**前两类只能人记**。

---

## 五、操作方式

```bash
# 平时用着觉得对/不对
cxa feedback ok
cxa feedback bad "用错命令了，该用 chapters 用了 info"

# 定期看健康度
cxa audit          # 看「Skill 健康」一节

# 手工记录 bad case
# 按第四节模板写到 docs/bad-cases/ 或 issue
```

**注意**：`feedback` **需要主动调**。不调就永远零记录，`任务成功率` 会一直显示「样本不足」——
**这是正确行为，不是 bug**。假装有数据比没有数据更糟。

---

## 六、这套评估的边界（必须对外说清）

**能保证的**：
- 格式通过率会随代码变化真的变（删一个 `--json` 顶层键就会红）
- 延迟有真实读数
- 覆盖率能看出"哪些命令从没被用过"
- 反馈样本够时能算成功率

**不能保证的**：
- **AI 有没有在该用的时候用**
- **用完用户满不满意**
- **用户有没有返工**

**如果用户问「这个 Skill 好不好用」，正确回答是**：
> 结构上的一致性我能证明（格式、延迟、覆盖）；
> **实际好不好用取决于 AI 会不会在合适的时候选它 —— 这一层我们测不了，只能靠你用的时候多点 `cxa feedback`。**
